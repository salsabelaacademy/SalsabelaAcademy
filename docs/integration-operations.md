# Phase 3 integration setup

## Deployment and environment

Run on a persistent Node server with PostgreSQL and outbound HTTPS to Zoom and Google. The in-process worker polls every 15 seconds; sleeping/serverless processes delay jobs until they run again. Never put these variables behind a `VITE_` prefix. Keep the existing session secret stable.

| Variable | Purpose |
| --- | --- |
| `DATABASE_URL` | Existing academy PostgreSQL connection |
| `SESSION_SECRET` | Existing server session secret |
| `FRONTEND_URL` | Exact public origin, e.g. `https://academy.example.com`; HTTPS in production |
| `INTEGRATION_ENCRYPTION_KEY` | Stable random 32-byte key, 64 hexadecimal characters; encrypts Google refresh tokens |
| `ZOOM_ACCOUNT_ID` | Zoom S2S app account ID |
| `ZOOM_CLIENT_ID` | Zoom S2S app client ID |
| `ZOOM_CLIENT_SECRET` | Zoom S2S app client secret |
| `ZOOM_HOST_USER_ID` | Academy instructor's Zoom user ID or email in that Zoom account |
| `GOOGLE_CLIENT_ID` | Google Web application OAuth client ID |
| `GOOGLE_CLIENT_SECRET` | Google OAuth client secret |
| `GOOGLE_CALENDAR_ID` | Optional owned calendar ID; defaults to `primary` |
| `TURNSTILE_SITE_KEY` | Public Turnstile site key for production account forms |
| `TURNSTILE_SECRET_KEY` | Server-side Turnstile secret |
| `RESEND_API_KEY` | Existing transactional email API secret |
| `RESEND_FROM` | Verified sender used for account email |
| `CONFIRM_PHASE3_MIGRATION` | Set to `yes` only for an explicitly reviewed production additive migration |

Generate the encryption key locally with `openssl rand -hex 32`, copy it into Secrets, and back it up privately. Changing it without re-encrypting existing grants requires reconnecting Google. Do not rotate it casually. Configure Turnstile for the hostname in FRONTEND_URL. The development bypass is only allowed with explicit `NODE_ENV=development` and no Turnstile secret.

Apply database changes before starting this release. See `START-HERE-AR.md` for separate existing/fresh database paths. No migration is run by server startup. SQL triggers in `0003` are essential for the transactional job outbox and are not generated by schema push.

## Zoom Marketplace: exact setup

1. Sign in to [Zoom App Marketplace](https://marketplace.zoom.us/) as the academy account owner or an administrator permitted to create S2S apps.
2. Open Develop / Build App and choose **Server-to-Server OAuth**, for this academy's own account. This is not Meeting SDK, a custom classroom, or legacy JWT.
3. Name the app `Salsabela Academy`, complete developer/contact information, and retain the Account ID, Client ID and Client Secret in server Secrets.
4. Add the following account-level granular scopes. They correspond only to the endpoints this implementation uses.

| Scope | Reason |
| --- | --- |
| `meeting:write:meeting:admin` | Create scheduled meetings |
| `meeting:update:meeting:admin` | Reschedule the existing meeting |
| `meeting:delete:meeting:admin` | Cancel meetings |
| `meeting:read:list_meetings:admin` | Reconcile ambiguous create results without creating duplicates |
| `meeting:read:meeting:admin` | Verify/recover meetings and retrieve the host start link |
| `user:read:user:admin` | Validate the selected host during connection testing |

5. Activate the app. Set ZOOM_HOST_USER_ID to the academy instructor's user ID or email, belonging to the same Zoom account. Account licensing and meeting limits still apply.
6. Restart the server after setting Secrets. Sign in as the academy admin, open `/admin/integrations`, choose Zoom Connect, then Test connection.
7. Create a future lesson for an active student, or confirm a dated assessment. Wait for the background job to succeed. Inspect the meeting in Zoom. Change its date and verify that the meeting ID stays the same. Cancel it and verify removal.

No Zoom redirect URI or webhook URL is needed for this S2S implementation. No webhooks are registered. Application-originated changes are synchronized; edits made directly in Zoom are not automatically imported.

Student responses contain only an authorized upcoming session's join URL. The start URL is never persisted, included in lists, or sent to students. The explicit authenticated admin **Start meeting** action retrieves the short-lived host URL on demand so the owner can launch Zoom; that capability necessarily reaches the admin's browser. API credentials and OAuth tokens never do. Do not forward host URLs.

The database commits `creating` before a Zoom POST. If a response is lost, retries inspect Zoom using the exact stored-resource agenda marker. If the remote result cannot be proven, the job stops as `zoom_create_uncertain` instead of creating another meeting. Use the admin recovery control with the matching Zoom meeting ID; it verifies the marker before adopting it. Do not delete integration rows or change FRONTEND_URL to bypass recovery. A failed create with no matching meeting requires operator investigation; the system deliberately does not promise automatic exactly-once creation when Zoom cannot prove the outcome.

References: [S2S OAuth](https://developers.zoom.us/docs/internal-apps/s2s-oauth/), [granular scopes](https://developers.zoom.us/docs/integrations/oauth-scopes-granular/), [Meetings API](https://developers.zoom.us/docs/api/meetings/).

## Google Cloud Console: exact setup

1. Sign in to [Google Cloud Console](https://console.cloud.google.com/) with the academy's Google account. Create or select a dedicated project.
2. In **APIs & Services → Library**, enable **Google Calendar API**, **Google Classroom API**, and **Google Drive API**.
3. Configure the OAuth consent screen / Google Auth Platform: academy app name, support email, developer contact, authorized domain, and real homepage/privacy-policy URLs. Choose Internal only if your Workspace organization supports it and all intended OAuth users are internal. Otherwise choose External and add the academy admin as a test user while testing.
4. In **Data Access**, add only the scopes in the table below. This application does not request Gmail, full Drive access, or domain-wide delegation.
5. In **Clients / Credentials**, create an **OAuth client ID → Web application**. Add this exact authorized redirect URI:

   `https://YOUR-ACADEMY-DOMAIN/api/integrations/google/callback`

   Replace the origin with FRONTEND_URL. For local development only, a separate registered URI may be `http://localhost:5000/api/integrations/google/callback`. For Replit use its actual HTTPS deployment origin. A preview origin and a published origin are different registrations. No browser-side OAuth client or JavaScript-origin flow is used.
6. Copy client ID and secret into server Secrets, set FRONTEND_URL and the encryption key, and restart.
7. Remain signed in to the academy platform as admin. Open `/admin/integrations` and connect Calendar, Classroom and Drive individually. During Google consent choose the same academy Google account. Each connection requests only its own scopes. Grant the requested permissions; partial grants are rejected.
8. Use Test connection for each service. Run a future lesson create/update/cancel test, a Classroom invitation test with an accepted active test student, and a private Drive assignment test. Check both the platform status and the provider's actual objects.
9. Before a public production rollout, complete Google's publication/verification requirements shown for your consent configuration and requested scopes. Testing-mode grants are not a substitute for production approval. Workspace administrators may also need to allow the app and Classroom invitations across domains.

| Google scope (prefix `https://www.googleapis.com/auth/`) | Purpose |
| --- | --- |
| `calendar.events.owned` | Create/update/delete events on calendars the connected account owns |
| `classroom.courses.readonly` | List the admin's existing courses and validate course visibility |
| `classroom.rosters` | Verify roster membership, course teacher authority, and send student invitations |
| `drive.metadata.readonly` | Inspect approved file metadata and sharing permissions without downloading file content or modifying sharing |

Drive metadata access is broader than one selected file because this workflow accepts existing resource IDs and must inspect permission metadata; it is read-only. A future Picker-based workflow could narrow resource selection, but is not implemented here. Assess Google's verification requirements for this scope in the console.

OAuth state is random, stored as a hash, tied to the exact admin session and service, expires in ten minutes and is consumed once. Refresh tokens are encrypted with AES-GCM and provider-bound authentication data. Replacement refresh tokens are retained encrypted. Revoked access produces an error and requires Reconnect.

Disconnecting any Google service clears all three local Google grants because Google's revocation may revoke authorization for the entire OAuth app. If remote revocation fails, local credentials are still removed and the UI asks for manual removal from the Google account's third-party access settings. Disconnect does not delete existing meetings, events, courses or shared files. Cancel sessions before disconnecting if those remote objects should be removed.

### Calendar behavior

Events belong to the admin's selected owned calendar. No student attendee email/invitation is sent automatically. Stable event IDs and stored calendar IDs avoid duplicate retries; changing GOOGLE_CALENDAR_ID affects new sessions, not existing ones. UTC instants are stored, Calendar receives an IANA timezone, and student screens use the student's profile timezone. Admin datetime inputs explicitly use the browser's local timezone; the separate IANA timezone controls calendar representation. At a DST overlap, API callers can provide explicit offsets to disambiguate instants.

Only the lesson/assessment title, timing and successful Zoom join URL enter Calendar. Private notes and host links never do. If Zoom creation fails, the combined job does not claim successful Calendar sync. Calendar can operate alone when Zoom has never been enabled for that resource.

### Classroom behavior

Use existing courses owned/taught by the connected academy admin. Link an active enrollment to one course. Only active student accounts with active enrollments can be invited; unaccepted applicants cannot use the flow. Because the admin cannot accept a student's Google consent, a new roster membership is shown as **Invited** until Google confirms membership. After acceptance, use the corresponding job retry or link action to check again. Existing membership is reconciled without a duplicate invitation. Domain policies and Google account eligibility may reject a real invitation; these are errors, not successful enrollment.

There are no platform teacher accounts. Course ownership remains in Google. Reassigning an existing link to another course is blocked to avoid silently leaving access behind. Removing Google Classroom membership is a manual Google action in this release.

### Drive behavior

1. In Drive, keep General access **Restricted**, and share the resource directly with the accepted student's email address. The student must be able to use that email with Google.
2. In Integrations, inspect the Drive URL/ID, choose the curriculum unit, and attach it. Public, domain-wide or group-shared resources are flagged and blocked by this private-resource workflow.
3. Assign the new material to an active enrollment in the same program. Existing assignments appear by ID, student name and title in the removal selector.
4. Students see only their assignments. Every Open action checks active enrollment, ownership, and current direct Drive permissions before returning a URL. A public URL alone never grants platform authorization.
5. Removing an assignment immediately removes platform access on the next request. It does not revoke a previously granted Google permission or copies already obtained. Remove the sharing permission in Drive separately when necessary. This is intentional: the integration has no write-sharing scope.

Legacy `googleDriveUrl` fields are no longer returned as authorized resources to students; reattach these through the inspected workflow. Non-Drive legacy resources retain their existing behavior.

Google references: [server OAuth](https://developers.google.com/identity/protocols/oauth2/web-server), [Calendar event insertion](https://developers.google.com/workspace/calendar/api/v3/reference/events/insert), [Classroom invitations](https://developers.google.com/workspace/classroom/reference/rest/v1/invitations/create), [Drive permission listing](https://developers.google.com/workspace/drive/api/reference/rest/v3/permissions/list).

## Reliability and operations

Jobs are persisted in PostgreSQL, deduplicated by resource key, and processed under a PostgreSQL advisory lock. Schedule triggers enqueue changes within the same database transaction. Generation counters keep an in-flight result from overriding a newer schedule. Retryable failures have a five-attempt limit and exponential backoff; terminal failures are shown for manual retry. Logs and stored errors use safe codes instead of provider bodies or tokens.

Keep the encryption key, origin and integration metadata stable across deployments. Database backups must include integration tables. Do not copy production job tables to a development environment that has live production provider credentials.
